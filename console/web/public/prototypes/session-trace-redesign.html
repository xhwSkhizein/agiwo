问题诊断（当前实现）→ 设计对策 不是换皮肤，而是换“人脑的默认阅读顺序”。

当前页面为什么难用

  1. 三套平行叙事：Objective 面板、Conversation events、Debug steps 并排堆叠，没有统一层级。
  2. 扁平化丢失结构：Trace spans 有 parent_span_id/depth，页面却按时间拍平成长链；Assignment 字段后端已有，前端未用。
  3. JSON 即详情：Step/Trace 默认露出 Raw JSON，掩盖“用户该看什么”。
  4. 交付与过程不分：P5-04 要求 Delivered 后报告置顶、过程折叠；现状仍像日志浏览器。
  5. 链接断裂：timeline 的 run_id 链到 traces 过滤，但列表不认 run_id。

新阅读顺序

  1. Outcome 顶栏（短）：只回答要不要介入 / 交付是什么。
  2. Assignment 标签：intake / work / verification 作上下文 chip，不占主栏。
  3. Runs + Steps 是主舞台：左侧选 run，右侧读步骤与工具调用。
  4. Objective 时间线极简：侧栏 3–4 句过程摘要，完整 facts 折叠。
  5. Trace：可点时间条（无独立 Span 树）+ 右侧分层详情。

数据契约已具备：RunResponse / StepResponse（含 depth/parent_run_id）、 assignments 作标签、timeline 作侧栏摘要、TraceDetail.spans 作下钻。

建议的页面职责切分

表面 回答的问题 真相源 默认深度
Sessions 哪些会话需要我介入？进展如何？ SessionSummary + 当前 Objective 状态摘要 状态 + 一句焦点
Session detail 这次 run 里发生了什么？工具/子 agent 做了啥？ RunLog → StepView（主）；ObjectiveView（辅） Runs 列表 + Steps；Outcome/标签/摘要靠边
侧栏过程摘要 交接/等待/交付发生过吗？ Objective timeline（压缩） 3–4 句；完整 facts 折叠
Trace detail 时间花在哪？某个 span 的 IO/成本是什么？ Trace/Span（RunLog 投影） 可点时间条 + 右侧分层详情

检查这份方案时请盯住这些点

  1. 进入 Session 后，目光是否自然落在 Runs + Steps。
  2. Assignment 是否只是一眼能扫过的标签，而不是又一组大卡片。
  3. Objective 时间线是否足够短，不抢 steps 的阅读带宽。
  4. 切换 run / child run 时，steps 是否立刻成为答案。
  5. Trace：点时间条后右侧详情是否清晰；深轨迹左侧滚动、右侧固定是否够用。
